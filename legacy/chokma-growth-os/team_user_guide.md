# CHOKMA Growth OS User Guide

คู่มือนี้อธิบายวิธีใช้งานระบบ **CHOKMA Growth OS** สำหรับทีมมาร์เก็ตติ้ง ทีม CRM และทีมปฏิบัติการ โดยเน้นการใช้งานจริงในสภาพแวดล้อมปัจจุบันของโปรเจกต์ที่เชื่อม **Landing Page**, **Dashboard Analytics**, **CRM สำหรับลูกค้าคุณภาพสูง**, และ **เส้นทางย้ายงานจาก Manual Broadcast ไปสู่ Automation** เข้าไว้ในระบบเดียว

ระบบถูกออกแบบให้สร้างมูลค่าทันทีแม้ยังอยู่ในช่วงพัฒนา กล่าวคือทีมสามารถเริ่มเก็บ lead, วัดผลแคมเปญ, ดูแลลูกค้าคุณภาพสูง, และบันทึก actual versus result ได้ตั้งแต่ตอนนี้ โดยไม่ต้องรอให้ broadcast automation ทำงานเต็มรูปแบบก่อน

| โมดูล | หน้าที่หลัก | ผู้ใช้หลัก | ผลลัพธ์ที่คาดหวัง |
| --- | --- | --- | --- |
| Landing Page | รับทราฟฟิกจากโฆษณาและเก็บ lead สำรอง | ทีม acquisition | ผู้ใช้กดสมัครจริงหรือทิ้งข้อมูลเข้า CRM |
| Dashboard | ดูภาพรวม lead, deposit, ROI, CPA และ actual vs result | ทีมมาร์เก็ตติ้งและผู้บริหาร | ตัดสินใจปรับแคมเปญได้เร็วขึ้น |
| CRM | ติดตาม lead มูลค่าสูง, deposit history และ follow-up notes | ทีม CRM | ปิดการขายและดูแลลูกค้าระยะยาวได้มีโครงสร้าง |
| Broadcast migration path | วางทางผ่านจาก manual ไปสู่ queue/automation | ทีมปฏิบัติการ | ลดงานกระจัดกระจายและเริ่มวัดผล planned vs actual |

## 1. เส้นทางการใช้งานประจำวัน

การทำงานประจำวันควรเริ่มจากการเข้า **Dashboard** เพื่อตรวจสถานะ lead ใหม่และผลลัพธ์ของแคมเปญก่อน จากนั้นทีม CRM จึงเข้า **CRM** เพื่อคัดเลือก lead ที่ควรติดตามต่อ โดยเฉพาะกลุ่มที่มีคะแนนคุณภาพสูงหรือถูกจัดระดับเป็น whale/vvip จากระบบคัดกรองทราฟฟิกแบบโปร่งใส

| ลำดับ | สิ่งที่ทีมควรทำ | หน้าที่ในระบบ |
| --- | --- | --- |
| ช่วงเช้า | เปิด Dashboard และดู lead ใหม่, ROI, CPA, actual vs result | ตรวจความเปลี่ยนแปลงตั้งแต่วันก่อนและดูว่ามีจุดเสี่ยงหรือไม่ |
| ระหว่างวัน | เปิด CRM เพื่อบันทึก note และดูประวัติการฝาก | เดินงานติดตามลูกค้าที่มีโอกาสสร้างรายได้สูงก่อน |
| ก่อนส่ง broadcast | อ้างอิง segment จาก Dashboard/CRM แล้วเลือกกลุ่มในเครื่องมือเดิม | ช่วงเปลี่ยนผ่านยังส่ง manual ได้ แต่ผลต้องบันทึกกลับเข้าระบบ |
| ปิดวัน | สรุปว่า action ไหนเกิดขึ้นจริงและได้ผลลัพธ์อย่างไร | เติม actual result, note หรือการเปลี่ยนสถานะ lead ให้ครบ |

## 2. การใช้งาน Landing Page และการรับ lead

หน้า Landing Page ของ CHOKMA ถูกออกแบบให้พาผู้ใช้ไปยังหน้าสมัครจริงของแบรนด์เป็นทางเลือกหลัก ขณะเดียวกันยังมีฟอร์มรับ lead สำรองสำหรับผู้ที่ยังไม่พร้อมสมัครทันที เมื่อผู้ใช้กรอกฟอร์ม ระบบจะเก็บข้อมูลติดต่อ, UTM, referrer, device type และนำข้อมูลดังกล่าวไปประเมิน **คะแนนคุณภาพทราฟฟิก** ฝั่ง server โดยอัตโนมัติ

แนวทางนี้ช่วยให้ทีมไม่ต้องคัดกรอง lead ด้วยความรู้สึกเพียงอย่างเดียว เพราะระบบจะให้ทั้งคะแนน, สถานะทราฟฟิก และการแจ้งเตือนเจ้าของระบบเมื่อพบ lead ใหม่หรือ lead คุณภาพสูง ซึ่งช่วยให้ทีมปฏิบัติการเข้าไปตอบสนองได้เร็วขึ้น

| ข้อมูลที่ถูกเก็บ | ใช้ทำอะไรต่อ |
| --- | --- |
| ชื่อ, เบอร์โทร, LINE ID | ใช้ติดตามต่อใน CRM |
| UTM source / medium / campaign | ใช้จับ attribution และวัดแคมเปญใน Dashboard |
| Referrer และ device type | ใช้ช่วยประเมินคุณภาพทราฟฟิกแบบโปร่งใส |
| Notes / intent | ใช้ช่วยจัดลำดับความสำคัญของ lead |

## 3. วิธีอ่าน Dashboard

หน้า Dashboard เป็นศูนย์ควบคุมสำหรับทีมมาร์เก็ตติ้งและเจ้าของระบบ โดยมีทั้ง snapshot metrics และมุมมอง **Actual vs Result** ที่ออกแบบให้เห็นความต่างระหว่างสิ่งที่ระบบตั้งใจทำกับสิ่งที่เกิดขึ้นจริง ตัวเลขหลักที่ควรดูทุกวันได้แก่จำนวน lead ใหม่, ยอดฝากสะสม, conversion rate, ROI, CPA รายแคมเปญ และจำนวนรายการที่ยังต้อง review

ในส่วน Actual vs Result ระบบจะแสดง planned actions, actual actions, completion rate, review required รวมถึงรายการ automation run ล่าสุด เช่น lead scoring ซึ่งมีทั้ง expected result, actual result และ review notes หากพบสัญญาณเสี่ยง เช่น notification ส่งไม่สำเร็จหรือทราฟฟิกน่าสงสัย ทีมควรใช้ข้อมูลส่วนนี้เป็นจุดเริ่มต้นของการตรวจสอบต่อ

| Metric | ความหมายเชิงปฏิบัติการ | ควรทำอะไรเมื่อค่าผิดปกติ |
| --- | --- | --- |
| Lead ใหม่ | จำนวน lead ที่เพิ่งถูกบันทึกเข้าระบบ | ตรวจว่า lead มาจาก source/campaign ใด |
| ยอดฝากสะสม | มูลค่าการฝากที่จับคู่กับ lead/campaign ได้ | เทียบกับ spend เพื่อดูกำไรขั้นต้นเชิง acquisition |
| ROI | ความคุ้มค่าของ spend ต่อผลลัพธ์จริง | หากต่ำต่อเนื่อง ให้ดู campaign performance แยกรายตัว |
| Estimated CPA | ต้นทุนต่อ lead/converted lead โดยประมาณ | หากสูงผิดเป้า ให้หยุดหรือปรับ creative และ targeting |
| Review required | งานหรือ lead ที่ระบบต้องการให้ทีมทบทวน | เข้าดูรายละเอียดใน actual vs result และ CRM |

## 4. วิธีใช้ CRM สำหรับลูกค้าคุณภาพสูง

หน้า CRM ถูกสร้างมาสำหรับการดูแลลูกค้าที่มีศักยภาพสูง โดยเฉพาะกลุ่ม VIP, VVIP และ whale ทีมงานควรเริ่มจากการเลือก lead เป้าหมาย จากนั้นใช้ note timeline เพื่อบันทึกสิ่งที่คุยไปแล้ว ข้อเสนอที่ลูกค้าสนใจ ช่องทางที่สะดวก และเวลาที่ควรติดตามครั้งถัดไป

การมี **deposit history** อยู่ในหน้าเดียวกันช่วยให้ทีมเห็นบริบททางรายได้ก่อนติดต่อกลับ เช่น ลูกค้าคนใดเพิ่งฝากครั้งแรก ลูกค้าคนใดเริ่มฝากซ้ำ หรือคนใดควรถูกขยับขึ้นสู่การดูแลระดับ VIP มากขึ้น ทั้งหมดนี้ทำให้การติดตามไม่หลุดเป็นชิ้น ๆ ระหว่างทีมมาร์เก็ตติ้งกับทีม CRM

| ฟังก์ชัน | การใช้งานที่แนะนำ |
| --- | --- |
| Whale profiles | ใช้ดูรายชื่อที่ควรได้รับการดูแลแบบใกล้ชิด |
| Lead selector | เลือก lead ที่จะเปิดดู timeline และ deposit history |
| CRM note | บันทึกข้อเสนอ, พฤติกรรม, ความชอบ และ next action |
| Deposit history | ประเมินมูลค่าลูกค้าและจังหวะในการ follow-up |

## 5. ระบบคัดกรองคุณภาพทราฟฟิกแบบโปร่งใส

ระบบใหม่ไม่ได้ใช้ cloaking หรือการปลอมหน้าใด ๆ แต่ใช้กฎเชิงข้อมูลที่ตรวจสอบได้ เช่น การมีข้อมูลติดต่อชัดเจน, UTM campaign ครบหรือไม่, referrer เป็นอย่างไร, device type ตรวจพบได้หรือไม่, และมีสัญญาณข้อความที่เข้าข่าย test/bot หรือไม่ ผลลัพธ์จะถูกสรุปออกมาเป็นคะแนนคุณภาพและสถานะทราฟฟิก เช่น **trusted**, **review**, หรือ **suspicious**

เมื่อระบบพบ lead คุณภาพสูง จะส่งการแจ้งเตือนไปยังเจ้าของระบบอัตโนมัติ และสร้างบันทึก actual vs result เพื่อให้ทีมเห็นได้ภายหลังว่ามีการคัดกรองอะไรเกิดขึ้นและผลเป็นอย่างไร หากระบบพบสัญญาณน่าสงสัยหรือการแจ้งเตือนส่งไม่สำเร็จ รายการนั้นจะถูกทำเครื่องหมายให้ review ต่อ

| สถานะทราฟฟิก | ความหมาย | แนวทางปฏิบัติ |
| --- | --- | --- |
| trusted | ข้อมูลครบและ attribution ชัด | ส่งต่อเข้า workflow ปกติของ CRM |
| review | คุณภาพพอใช้แต่ยังควรตรวจเพิ่ม | ให้ทีมตรวจ notes และ source ก่อน follow-up หนัก |
| suspicious | พบ pattern ที่เข้าข่าย test/bot หรือข้อมูลขาดมาก | อย่าใช้ตัดสินใจเชิง spend ทันที ควร review ก่อน |

## 6. การย้ายงานจาก Manual Broadcast / Broadpung

ในระยะปัจจุบัน ทีมยังสามารถใช้เครื่องมือ broadcast เดิมต่อได้ แต่ควรใช้ CHOKMA Growth OS เป็นแหล่งข้อมูลหลักของ lead, profile, deposit และผลลัพธ์จริงเสมอ หลักการสำคัญคือ **ส่งจากที่เดิมได้ แต่ต้องบันทึกผลกลับเข้าระบบเดียว** เพื่อไม่ให้ข้อมูลกระจัดกระจาย

แนวทางปฏิบัติคือให้ทีมดึงรายชื่อเป้าหมายจาก Dashboard หรือ CRM, เตรียมข้อความในเครื่องมือเดิม, ส่งข้อความตาม workflow ที่ใช้อยู่ แล้วกลับมาบันทึก note, ผลตอบกลับ, deposit outcome และสรุป planned vs actual ในระบบใหม่ เอกสารรายละเอียดเชิง migration เชิงลึกยังดูต่อได้ที่ไฟล์ `broadcast_migration_path.md`

| ช่วงเปลี่ยนผ่าน | สิ่งที่ยังทำแบบเดิม | สิ่งที่ต้องทำในระบบใหม่ |
| --- | --- | --- |
| Manual-first | ส่ง broadcast ด้วยมือทั้งหมด | บันทึก lead, segment, note และผลลัพธ์ |
| Assisted | ทีมยังเป็นคนส่ง | ใช้ Dashboard/CRM ช่วยจัดลำดับและดูผลจริง |
| Queue-based | ทีมอนุมัติก่อนส่ง | บันทึก queue, objective และ planned vs actual |
| Automation-ready | ทีมดูเฉพาะเคสสำคัญ | ใช้ trigger อัตโนมัติสำหรับ lead/value events |

## 7. ขั้นตอนเปิดใช้งานจริง

การเปิดใช้งานจริงควรทำแบบเป็นลำดับเพื่อให้ทีมมั่นใจว่าข้อมูลทุกชั้นเชื่อมกันแล้ว ก่อนเริ่มยิงทราฟฟิกเต็มรูปแบบ ควรทดสอบเส้นทางตั้งแต่การเปิด Landing Page, การส่ง lead, การขึ้นข้อมูลใน Dashboard, การเห็น lead ใน CRM และการส่งการแจ้งเตือนของเจ้าของระบบให้ครบก่อน

| ขั้นตอน | สิ่งที่ต้องตรวจ | สถานะที่ควรได้ |
| --- | --- | --- |
| 1. เปิด Landing Page | CTA ชี้ไปหน้าสมัครจริง | ปุ่มทุกจุดเปิดลิงก์สมัคร CHOKMA ได้ |
| 2. ส่ง lead ทดสอบ | ฟอร์มบันทึกข้อมูลพร้อม UTM/referrer | Lead ใหม่ขึ้นใน Dashboard และ CRM |
| 3. ตรวจ Dashboard | Snapshot และ campaign cards อัปเดต | เห็น lead count, ROI/CPA และ actual vs result |
| 4. ตรวจ CRM | เลือก lead แล้วดู note/deposit history | สร้าง note ได้และอ่านประวัติการฝากได้ |
| 5. ตรวจ notification | ระบบส่ง owner alert เมื่อมี lead ใหม่ | เจ้าของระบบได้รับการแจ้งเตือน |
| 6. เริ่ม traffic จริงแบบจำกัดงบ | ดูคุณภาพ lead รอบแรก | ใช้ Dashboard/CRM ปรับกลยุทธ์ก่อน scale |

## 8. ข้อควรระวังในการใช้งาน

ระบบนี้ไม่ควรถูกใช้เพื่อทำ cloaking, หลบการตรวจจับ หรือปลอมหน้าสำหรับหลบ policy ของแพลตฟอร์มโฆษณา การคัดกรองทราฟฟิกที่มีอยู่ในระบบเป็นการประเมินเชิงข้อมูลเพื่อช่วยจัดลำดับการทำงานของทีมเท่านั้น ไม่ใช่กลไกหลอกผู้ใช้หรือแพลตฟอร์ม

หากทีมต้องการขยายต่อในเฟสถัดไป งานที่ควรทำทันทีคือการเพิ่ม queue manager สำหรับ broadcast, mutation สำหรับจัดการ queue, logging ผลส่งจริง, และเครื่องมือ import ข้อมูลจาก CSV/Google Sheets อย่างปลอดภัย โดยยังคงใช้ระบบนี้เป็นแหล่งข้อมูลหลักเสมอ
