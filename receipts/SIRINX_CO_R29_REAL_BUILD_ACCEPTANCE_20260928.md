## What was actually done

Replaced a harness-based verification with the project's real acceptance path: a production
build, served by `vite preview`, driven through four actual routes with Playwright and the
installed Chrome. Also measured the production bundle for both flag states, which was the
gap I had previously recorded as unmeasured and as the thing that would decide the motion
question.

## The mistake, and the repair

I ran `rm -rf dist/public` followed by `npx vite build`, which is a partial build. The
project's real build also runs `server/staticSeoBuild.ts` to produce prerendered HTML, and
`shared/crawlReachability.test.ts` walks the `<a href>` graph in that output. The suite
went to **2 failed / 356 passed** and stayed there until the full `npm run build` restored
108 prerendered files.

Verified afterwards: **47 files / 358 tests passed, `tsc --noEmit` exit 0**, flag confirmed
at `false`, both servers stopped with 0 processes remaining.

## Correction recorded

My first real-route reading reported the canvases as still animating under
`prefers-reduced-motion`, which would have meant the fix did not hold in production. It
does hold: the 3D issues **zero** `requestAnimationFrame` calls under reduce, against 274
when animating. The canvas rectangle moved because page-level motion shifts pixels inside
it — proven by a static `<h1>` control region that moved too.

This supersedes the earlier harness-based "verified" claim, which was a synthetic fixture
and would not have caught this.

## Findings

1. All three 3D fixes hold on the shipped route, not only in isolation.
2. All four real routes return 200 with zero page errors; the homepage mounts one live WebGL
   canvas and the province route two.
3. Enabling motion costs **+0.5 kB raw / +0.2 kB gzip** across the whole bundle, because
   `vendor-motion` is already shipped for 13 other pages. With the runtime result
   (+4 ms / +8 ms median LCP, CLS unchanged), both objections to the motion flag are now
   measured rather than argued.
4. `npm test` in this repo silently depends on a full build being present. A partial build
   yields a red suite whose message points at crawl links rather than at the build. This
   will mislead the next person and is worth documenting in the repo's own AGENTS.md.
